### 一、讨论与心得

#### (1) 本实验中，如何保证数据帧的完整性。此方法与字节填充方法相比，有什么优点或缺点，分别适用于什么场合？

**保证数据帧完整性的方法：**

**超时机制（物理/时间层）：** 系统利用定时器（TIM1）实现超时判断 。当接收到一个字节后重置定时器，若字节间隔超过 2ms 或两帧间隔大于 2ms，则认为当前帧接收结束或发生异常 。


**校验和机制（协议层）：** 帧格式中定义了 `SUMH` 和 `SUML` 两个字节的校验位 。接收方在收到完整帧后，通过 `CheckFrameSum` 函数计算数据部分的累加和，并将其与接收到的校验和进行比对，若不一致则判定帧损坏 。


**停止等待 ARQ（控制层）：** 采用主动发送命令帧并返回确认帧的机制，确保每一帧都被正确接收 。

**与字节填充法相比：**


**优点：** 协议处理简单，不需要对数据载荷中的特殊字符（如标志位 `0x7E`）进行转义处理，能够保持数据的透明传输，且协议开销较低 。


* 
**缺点：** 对系统的实时性要求极高 。如果系统任务繁重导致中断响应延迟超过 2ms，会产生误判 。


* **适用场合：**
* **超时方法：** 适用于实时性较好、处理器负担较轻且通信速率固定的同步或准同步场合（如 Modbus RTU 工业协议）。
* **字节填充法：** 适用于定时不确定的异步链路，或延时抖动较大的网络环境（如 HDLC 或 PPP 协议）。



#### (2) 如可以重新修改数据链路层协议，有哪些方法可以加快图片下载速度？

* 
**引入滑动窗口协议：** 目前采用的是停止等待 ARQ，即每发一帧都要等待确认，效率较低 。改为滑动窗口协议（如连续 ARQ 或选择重传 ARQ）可以允许连续发送多个帧而无需立即等待确认。


* 
**增大单帧数据载荷：** 目前单帧最大长度限制为 1000 字节 。在信道质量较好的情况下，增大单帧长度可以降低帧头和确认帧带来的协议开销比例。


* 
**数据压缩：** 在文件传输层之前对图像点阵数据进行压缩（如 RLE 算法），减少需要传输的总字节数 。


* **提高硬件波特率：** 在物理层提高串口通信的波特率，直接缩短每个位的传输时间。
* **简化确认机制：** 采用“否定确认”（NAK）模式，仅在发现错误时请求重发，而在正常情况下不发送确认帧。

**不能显示的原因：**

* 
**内存容量限制：** 实验中定义的图像缓冲区为 `uint8_t FileBuff[100000]`，即 100,000 字节 。


* 
**计算需求：** LCD 采用 RGB565 格式，每个像素占用 16 位（2 字节）颜色深度 。


* **存储缺口：**  分辨率的图片总像素为 76,800 个，所需内存空间为  字节。当前的 `FileBuff` 容量远小于此需求，会导致缓冲区溢出或数据丢失。

**处理方法：**

* 
**扩充内部缓冲区：** 尝试增大 `FileBuff` 数组的大小至 153,600 字节以上。但这取决于 STM32 芯片的内部 SRAM 剩余空间 。


* 
**利用外部 SRAM：** 实验板配置了 FSMC（灵活静态存储控制器）。可以利用 FSMC 扩展外部存储器（如 SRAM 芯片），将 `FileBuff` 指向外部地址空间以获得更大的存储能力 。


* 
**边收边发（分块显示）：** 改变编程策略，不再等待文件全部接收完成后再调用 `Show_bmp` 。可以根据接收到的数据帧序号，实时计算坐标并直接写入 LCD 的 GRAM，从而避免占用大量连续内存 。
